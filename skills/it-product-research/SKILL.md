# IT 产品竞品调研 Skill

## ⚠️ 执行前提（STOP — 必做，不可跳过）

**在调用任何网页搜索/抓取工具，或撰写任何报告内容之前，你必须先完成第零阶段的需求澄清。**（本 skill 不绑定特定工具名，见末尾「搜索工具使用指南」）

- 这是一道硬门槛：未提问即开始搜索 = 调研失败，口径会与用户预期不一致。
- 即使用户的请求看起来已经"很明确"，也必须先提问确认筛选标准与权重偏好——不同权重会产生完全不同的排名（这正是历史上两次调研结果不一致的根因）。
- 唯一可跳过提问的情况：用户在本轮对话中已经主动、完整地指定了全部 5 项偏好（筛选标准、侧重维度、开源/闭源、部署要求、预算）。此时在报告头部注明"用户已显式指定偏好，跳过提问"。

### 提问方式（二选一，按优先级）

1. **优先**：调用 `question` 工具，一次性批量提出第零阶段的全部问题。这样用户能通过结构化选项 + "Type your own answer" 快速作答。
2. **兜底**：如果 `question` 工具不可用、或你不确定它是否可用，**直接以普通文本输出第零阶段的全部问题**（按下方模板逐条列出，含选项），然后**停止本轮输出、等待用户回答**，不要继续搜索。用户回答后再进入第一阶段。

> 关键：无论用哪种方式，你都必须在搜索前**停下来等待用户回答**。绝不能"自问自答"或跳过提问直接搜索。

## 概述

本 Skill 指导你如何系统化地完成 IT 产业产品的竞品调研，生成专业的横向对比报告。调研遵循"**需求澄清 → 粗查 → 动态定义维度（先出草案，请客户修订）→ 核实维度是否合理 → 精化维度 → 深挖 → 评分 → 中英双语输出**"的流程。维度数量和内容随产品领域和用户偏好**动态调整**，不固定为 10 个。

## 调研流程

### 第零阶段：需求澄清（交互式提问）

在开始任何搜索之前，**必须**先向用户提问，明确本次调研的筛选标准、权重偏好和产品池范围。这一步直接决定后续的产品入选与最终排名，**不可跳过**。

#### 提问方式

按「执行前提」中的二选一规则：
- **方式A（优先）**：调用 `question` 工具，将下方 5 个问题作为 `questions` 数组一次性提交
- **方式B（兜底）**：直接以纯文本输出下方"纯文本提问模板"，然后停止输出、等待用户回答

#### 提问规范

- 所有问题一次性提出，不要逐条追问
- 每个问题提供 3-5 个选项；**不要**自己添加"其他/以上都不是"等兜底选项——`question` 工具默认启用 `custom`，会在每个问题末尾自动追加"Type your own answer"选项，用户可自由输入；纯文本模式下则在每题末尾写明"或自行补充"
- 需要多选的问题标注"（可多选）"
- 若有推荐项，放在选项列表第一位并标注"(Recommended)"
- 用户若选择自由输入或拒绝回答，按其文本理解后继续，并在报告头部注明权重依据来源

#### 必须提出的问题

**Q1：本次调研的筛选标准侧重？**（单选）
- "Triage + 知识库并重 (Recommended)" — 同时要求 Triage Agent 能力与知识库实现
- "以 Triage 为核心能力" — 仅纳入分诊/告警分类/优先级排序为专长的产品
- "通用事件管理 + AI 增强" — 纳入传统事件管理平台中的 AI 能力
- "特定领域分诊" — 如安全告警、ITSM 工单等垂直领域

> 说明：该选择直接写入报告头部的"筛选标准"字段，并决定产品入选门槛。例如选"Triage+知识库并重"会纳入同时具备两者实现的产品（如 Aurora、NeuBird），排除仅有分诊能力但无知识库的产品。

**Q2：你最看重的能力区域是哪些？**（多选，`multiple: true`）

> 注：这些是能力区域，不是固定维度。第一阶段会根据你选的区域 + 产品领域动态生成维度草案，第二阶段与你确认并精化为最终维度（6-12 个）。

- "核心功能" — 如分诊/告警降噪/准确率/处理速度
- "知识/数据底座" — 知识图谱/向量检索/历史学习
- "分析推理" — 根因分析/因果推理/证据链
- "集成与互操作性" — API/MCP/生态集成数
- "自主性与可控性" — Agent 自主级别/安全护栏
- "成本与定价" — 起价/免费层/隐性成本
- "部署与数据主权" — SaaS/私有化/数据驻留
- "开源与可定制" — 源码开放/自定义能力

> 说明：被选中的能力区域在综合评分中设为"高"权重，未选中的设为"中/低"。这避免了不同次调研因隐含权重不同而导致排名反转。

**Q3：开源 vs 闭源偏好？**（单选）
- "不限，两者都纳入 (Recommended)" — 开源和闭源都调研对比
- "偏好开源" — 优先开源方案，闭源仅作参照
- "偏好闭源/商业" — 优先企业级 SaaS，开源仅作参照
- "仅开源" — 只调研开源项目
- "仅闭源" — 只调研闭源商业产品

**Q4：部署与数据驻留要求？**（单选）
- "SaaS 即可 (Recommended)" — 接受云端 SaaS 部署
- "需要私有化/本地部署" — 数据不出企业网络
- "需要 VPC 部署" — 数据在客户云环境内
- "混合模式" — SaaS + 本地 Agent

**Q5：预算与成本敏感度？**（单选）
- "不限，以能力优先 (Recommended)" — 不设预算上限
- "有预算上限" — 需要考虑 TCO
- "优先免费/开源" — 预算有限，优先免费方案
- "需要公开定价" — 排除"联系销售"的不透明定价


#### 回答处理

| 回答 | 影响 |
|------|------|
| Q1 筛选标准 | 写入报告"筛选标准"字段；决定产品入选门槛 |
| Q2 能力区域偏好 | 第一阶段据此动态生成维度（选中区域=高权重，其余=中/低）；写入综合评分表说明 |
| Q3 开源偏好 | 决定产品池是否纳入开源/闭源项目 |
| Q4 部署要求 | 过滤不符合部署模式的产品；标注数据驻留 |
| Q5 预算敏感度 | 决定是否排除不透明定价产品；标注成本评级 |

完成需求澄清后，进入第一阶段。将用户的回答摘要记录在报告头部的 metadata 区块中（示例）：

```markdown
> 调研时间：YYYY-MM-DD
> 筛选标准：Triage + 知识库并重（用户选择）
> 评估维度：8 个（依据用户能力区域偏好 + 产品领域动态生成）
> 权重依据：用户侧重 [核心功能, 知识/数据底座, 分析推理] → 高权重；其余 → 中/低
> 产品池范围：开源+闭源均纳入；SaaS 部署；预算不限
```

### 第一阶段：动态定义评估维度

**不要使用固定维度**。维度的选择应取决于调研的产品领域和用户在第零阶段 Q2 中选择的侧重方向。

1. 根据用户的调研目标，先做一轮**粗浅搜索**（用当前环境中任何可用的网页搜索工具），了解该产品领域的基本情况、主要玩家和产品形态
2. 根据粗查结果 + 用户 Q2 选择的侧重方向，从下方「维度参考库」中**选取或派生 6-12 个评估维度**。选取原则：
   - 用户 Q2 选中的能力区域**必须**包含对应维度
   - 根据产品领域特点增补**领域专属维度**（如安全产品加"威胁情报覆盖/MITRE 映射"，ITSM 加"工单路由/SLA 管理"，可观测性加"数据源覆盖"）
   - 删除与该领域明显不相关的维度
   - 维度数量建议 6-12 个：太少则对比粗糙，太多则评分疲劳
3. 将维度列表整理为**草案**，每个维度附上权重（依据 Q2：选中的能力区域=高权重，其余=中/低）和选取理由
4. **提交客户审阅**：输出维度草案后**必须停下来等待客户确认或修订**。提示客户可以增减维度、改名、调整权重。提交方式同第零阶段（优先 `question` 工具，兜底纯文本输出后停止）。

> 关键：维度草案必须经客户确认后才能定稿。绝不能跳过审阅直接深挖——维度一旦确定，后续所有对比和评分都基于它。

#### 维度参考库

以下维度按能力区域分组，供选取/派生时参考（非全部必选，也非穷举——可根据领域自由派生新维度）：

| 能力区域 | 候选维度 | 典型可量化指标示例 |
|---------|---------|-------------------|
| 核心功能 | 核心能力 / 告警降噪 / 准确率 / 处理速度 / 吞吐量 | 降噪率 95%、12 秒、100% 准确 |
| 知识/数据 | 知识图谱 / 知识库 / 向量检索 / 历史学习 / 组织记忆 | 自动更新、多数据源、检索质量 |
| 分析推理 | 根因分析 / 因果推理 / 证据链 / 爆炸半径 / 预测能力 | 自动化程度、置信度评分 |
| 集成互操作 | API / MCP / 生态集成数 / 双向同步 / Slack 原生 / Webhook | 集成数量、开放协议 |
| 自主可控 | Agent 自主级别 / Human-in-the-Loop / 安全护栏 / 可审计 / RBAC | L1-L4、权限控制 |
| 成熟稳定 | 成立时间 / 客户规模 / 合规认证 / SLA / 融资轮次 / 社区活跃度 | SOC 2、ISO 27001、Star 数 |
| 部署运维 | SaaS / 私有化 / 数据驻留 / 运维复杂度 / 资源消耗 / 离线可用 | VPC、本地、混合 |
| 成本定价 | 定价模型 / 起价 / 隐性成本 / 免费层 / TCO / 开源免费 | $/用户/月 |
| 扩展定制 | 多租户 / 自定义规则 / 自定义 Agent / 插件生态 / API 开放度 | 企业级、可扩展 |
| 创新趋势 | 技术路线 / MCP / 因果推理 / 多 Agent / 路线图 / 开源策略 | Agentic AI |
| 领域专属 | （由产品领域决定，需自行派生） | 如安全的 MITRE 覆盖、ITSM 的工单路由、可观测性的数据源覆盖 |

> 关键：Q2 选中的能力区域必须覆盖；领域专属维度体现不同产品领域的差异。最终维度列表写入报告头部 metadata。

### 第二阶段：核实与精化维度

1. **核实维度合理性**：检查客户修订后的维度集是否满足：
   - 覆盖了客户 Q2 选中的所有能力区域
   - 无明显遗漏（如客户关心成本但未纳入定价维度 → 补回）
   - 无冗余（如两个维度高度重叠 → 合并）
   - 每个维度可量化、可横向对比
   - 维度数量在 6-12 个合理区间
2. **精化定稿**：根据客户反馈调整维度名称、数量、权重，形成**最终维度列表**
3. 将最终维度列表写入报告头部 metadata，后续所有阶段均以该列表为准

### 第三阶段：深挖详情

对每个候选产品，进行**多轮搜索**收集各方面信息：

1. 搜索产品官网，获取核心功能、定价、客户案例
2. 搜索产品对比评测文章（如 "X vs Y comparison"）
3. 搜索技术博客、社区讨论获取真实评价
4. 对开源项目，参考 GitHub 的 README、Star 数、最近更新时间
5. 使用 URL 读取工具读取产品官网获取详细信息（注意：部分网站可能屏蔽爬虫）
6. 搜索视频资源（如官网 Demo、YouTube 教程、B站视频）

**搜索提示**：使用多个不同关键词组合搜索同一产品，避免遗漏信息。优先使用英文搜索 + 中文搜索双线并行。

### 第四阶段：产品分组

将产品按类型分组（如：闭源 SaaS / 开源项目），每组内按 Triage 专注度或核心能力排序。

### 第五阶段：各维度详情展开

为每个产品撰写结构化的详情，使用表格形式按第二阶段精化后的最终维度逐一展开：

```markdown
### 产品名称

- **官网**：https://...
- **成立时间**：YYYY
- **类型**：闭源 SaaS / 开源

| 维度 | 详情 |
|------|------|
| **维度1** | 具体描述，包含关键数据指标（如百分比、秒数） |
| **维度2** | 具体描述 |
| ... | ... |
```

**关键原则**：每个维度的描述要包含**可量化指标**（如降噪率 95%、MTTR 降低 50%、12 秒完成分诊），而非泛泛而谈。

### 第六阶段：横向对比表格

按维度生成横向对比表，每个维度一张表，所有产品在同一行：

```markdown
### 3.1 分诊能力

| 产品 | 指标1 | 指标2 | 指标3 | 指标4 |
|------|------|------|------|------|
| **产品A** | 数据 | 数据 | 数据 | 数据 |
| **产品B** | 数据 | 数据 | 数据 | 数据 |
```

每张表选取该维度下最关键的 4-5 个子指标。

### 第七阶段：综合评分

1. 为每个维度打分（1-10 分制，10 分最优）
2. 生成综合评分表，所有维度分数 + 总分一目了然
3. 附评分说明：**权重依据第零阶段用户的能力区域偏好回答**，选中区域对应的维度为"高"权重，其余为"中/低"。不得使用隐含默认权重

### 第八阶段：中英双语报告

1. 先完成中文版报告
2. 翻译为英文版，注意专业术语对照：
   - 分诊 → Triage
   - 告警降噪 → Alert Noise Reduction
   - 知识图谱 → Knowledge Graph
   - 根因分析 → Root Cause Analysis (RCA)
   - 爆炸半径 → Blast Radius
   - 隐性知识 → Tribal Knowledge
   - 因果推理 → Causal Inference
   - 零幻觉 → Zero Hallucinations
   - 人机协作 → Human-in-the-Loop
   - 安全护栏 → Guardrails
   - 可解释性 → Explainability
   - 多租户 → Multi-Tenancy
   - 吞吐量 → Throughput
   - 自主级别 → Autonomy Level
   - 部署方式 → Deployment Model
   - 数据驻留 → Data Residency

### 第九阶段：结论与推荐

按综合评分排序，给出推荐排名和场景建议：

```markdown
| 排名 | 产品 | 核心优势 | 推荐场景 |
|:----:|------|---------|---------|
| 1 | **产品A** | 优势描述 | 场景描述 |
```

## 报告结构模板

最终报告应包含以下章节：

```

> 筛选标准：xxx（用户选择）
> 评估维度：N 个（依据用户能力区域偏好 + 产品领域动态生成）
> 权重依据：用户侧重 [能力区域A, 能力区域B, ...] → 高权重；其余 → 中/低
> 产品池范围：开源/闭源偏好、部署要求、预算敏感度

## 一、闭源产品
### 1. 产品A
### 2. 产品B
...

### N. 项目X

### 3.1 维度1
### 3.2 维度2
```

| 能力 | 用途 | 匹配示例（不限于这些） |
|------|------|----------------------|
| 网页搜索 | 产品搜索、功能查询、对比评测 | `MiniMax_web_search`、`searxng_searxng_web_search`、`websearch` 等任意可用搜索工具 |
| URL 读取 | 读取官网/文档获取详细信息 | `searxng_web_url_read`、`webfetch` 等任意可抓取网页内容的工具 |
| 图像理解 | 分析产品截图/架构图 | `MiniMax_understand_image` 等 |
| 浏览器自动化 | 需要交互才能获取的信息 | `playwright_browser_*` 等（优先级最低） |

**原则**：
- 先探测当前环境有哪些工具可用，按能力匹配，而非按工具名调用
- 搜索时应批量并行发起多个搜索请求以提高效率
- 先搜索产品名称 + 核心功能，再搜索产品名称 + 对比/评测/定价等细节
- 优先使用英文搜索 + 中文搜索双线并行
- 如果某类工具不可用，跳过对应能力，用其他工具替代或在报告中标注信息缺口
